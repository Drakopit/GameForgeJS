# Create a project

Use a minimal executable starter for a new game. The larger repository
examples demonstrate integrated features and are not application templates.

## Generate and run

The CLI is optional. For a manually created game, keep a copy of the engine's
`src` directory under `engine`, add an HTML entry that loads `main.js` as a
module script (`type="module"`), and import `BootstrapGame`
from `./engine/core/index.js`. Serve the directory with any static HTTP server.
Use relative imports to the same engine copy in your levels and entities.
No npm package, generated module registry or build is required for this path.

For 2D, extend `Level`, create `Screen` in `OnStart`, pass it to `Draw` and
your `GameObject` entities, and register entities with `AddEntity`. Call
`super.OnStart(context)` after construction. The starter below demonstrates
that same framework lifecycle; the CLI only automates file creation.

From an engine checkout:

```sh
node cli/index.cjs create ../my-game --template minimal-2d
node cli/index.cjs serve --root ../my-game
```

Open the address printed by the server. Choose `minimal-3d` to start a
WebGL2 project instead. The destination must be empty.

The CLI uses the local engine by default and writes a local package
dependency. To use the generated project's npm scripts, run `npm install`
inside that project, then `npm run dev`. You can also keep invoking the
engine checkout's CLI with `--root`, as above.

## Project structure

```text
my-game/
  index.html                 Browser document and public import map
  main.js                    Game composition and startup
  config/
    gameforge.project.json   CLI metadata and extension registration
    gameforgejs.package.json Runtime groups for publication
    game.config.json         Runtime settings owned by this game
    resources.json           Asset declarations
  package.json               Local engine dependency and npm scripts
  src/
    modules.js               Registry generated by the CLI
    ...                      Game-specific code from the selected starter
  assets/                    Add game resources here as needed
```

The starter files themselves are authoritative. Inspect
`cli/templates/minimal-2d/` or `cli/templates/minimal-3d/` in the engine
checkout to see exactly what a new game receives.

Keep new levels, screens, entities, and systems under `src/` when needed.
Avoid empty architectural layers that have no responsibility yet. The root
entry should compose the game rather than contain all its gameplay.

## Follow the game patterns

```js
// main.js
import { BootstrapGame, Level } from "gameforgejs/core";

class FirstLevel extends Level {}

BootstrapGame({
  configPath: new URL("./config/game.config.json", import.meta.url).href,
  levels: [new FirstLevel()],
});
```

The CLI starters use the established bootstrap and inheritance pattern:
`BootstrapGame` starts registered levels, levels extend `Level` (or `Level3D`),
and 2D entities extend `GameObject` so levels can own them with `AddEntity`.
The 3D starter composes renderable objects in `Level3D.BuildScene()`.
`gameforge generate` creates classes that follow the selected starter's pattern.

The starter's import map resolves public names through `./@engine/`. During
development, the CLI serves that URL from the selected engine. A static build
copies the runtime to the same URL structure. The separate `createGame`
instance API remains available for projects that explicitly need it; it is not
required to adopt the CLI's default game pattern.

Do not change imports to `../../src/...` or `packages/...` when moving
your game. Change the dependency or CLI engine location instead.

## Configuration ownership

New starters also include `gameforgejs.package.json` to select runtime groups
for publication. It does not alter startup or create framework services.
See [Distribution packages](../reference/distribution-packages.md).

`gameforge.project.json` belongs to tooling: schema version, HTML entry,
runtime config filename, resource filename, selected official modules, and
local engine location.

`game.config.json` belongs to the game: screen, input, audio, and gameplay
settings. Engine defaults are defined in the runtime, so a new game does not
need a second root-level defaults file.

`resources.json` declares assets. Adding an asset declaration does not
instantiate an entity or assign gameplay behavior.

An optional `game.workspace.json` belongs to an external authoring tool.
It is not another runtime configuration file. See the
[editor contract](../tools/world-editor-v4.md).

## Add behavior

```sh
node cli/index.cjs generate level ForestLevel --root ../my-game
node cli/index.cjs generate entity Player --root ../my-game
node cli/index.cjs add audio --root ../my-game
```

The module registry in `src/modules.js` is generated. Keep custom module
implementations in their own files and pass `createModules()` to
`BootstrapGame` from the game's entry. Register generated levels in the
`levels` array in `main.js`; add generated 2D entities to a level with
`AddEntity`. Generated 3D objects must be added to a level's scene in
`BuildScene`. Generation creates starter source files but does not silently
change the game's composition.

## Resources and paths

Keep asset paths relative to the game document, not to the engine checkout.
For example, a resource manifest for a game whose `index.html` is at its
root may register:

```json
{
  "images": [
    { "name": "player_idle", "path": "./assets/player/idle.png" }
  ],
  "audios": [
    { "name": "jump", "path": "./assets/audio/jump.wav" }
  ],
  "jsons": [
    { "name": "first_level", "path": "./assets/levels/first.json" }
  ]
}
```

Those files are illustrative; create or copy the actual assets your game
uses. A resource declaration must point to an existing file.

When a new game needs manifest loading, add `manifestPath` to its existing
`createGame` options:

```js
manifestPath: new URL("./config/resources.json", import.meta.url).href,
```

The game initializes its modules before loading that manifest. For example,
audio decoding needs the audio module, and model loading needs the 3D module.
The empty starter manifest does not imply that arbitrary resources load
automatically without this option.

## Check and build

```sh
node cli/index.cjs doctor --root ../my-game
node cli/index.cjs build --root ../my-game
```

Serve the generated `dist/` directory through a static HTTP server and test
it separately from the engine checkout. A build is a static copy, not a
bundling or minification step.
